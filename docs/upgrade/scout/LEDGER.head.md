# Upgrade ledger and coverage map

Decision record of the kit upgrade of 10 to 13 November 2026. Every candidate that the research looked at has one
row below: {N_ROWS} rows from 31 research notes (`docs/upgrade/scout/draft/`). This file is generated by
`docs/upgrade/scout/make_ledger.py build` from those notes; edit the notes or `scout/LEDGER.head.md`, not this file.

| Decision | Rows | Meaning |
|---|---|---|
| Adopt | {N_ADOPT} | evidence says it helps a real use of the kit. {ADOPT_FINISHED} are finished, {ADOPT_UNFINISHED} are not; the Status column says where or why |
| Trial | {N_TRIAL} | undecided, worth a test; the row names the test |
| Assess | {N_ASSESS} | undecided, only looked at; the row names the test |

## How far this ledger goes, and where it stops

- The research was done by parallel research agents on 10 and 11 November 2026, each row with its source and the date
  it was checked. Two reports the user supplied (ChatGPT and Gemini deep research) went in as the note `user-reports`.
- On 11 November the user limited the upgrade to the most important items, because of the usage limit of the model
  doing the work. From then on: no second verification round of the notes, no reconciliation round between scouts, and
  no trial runs for the undecided rows. That is the reason every Trial and Assess row is still undecided.
- "Finished" for an adopted row means what the upgrade prompt defines: a feature is built, tested and documented; a
  technique has a reference that says when and how to use it, with its source; a third-party tool has a documented
  enabling step at a pinned version that was run here. Three reading agents checked the 265 adopted rows that no
  reference covers against the kit's files and marked each one; partly built counts as unfinished.
- Most unfinished rows are refinements of things that exist (a stricter noise floor, a doctor command,
  minimum-version gates). They were not built for the reason above. None of them is needed for the four required
  features to work; each is a candidate for the next round.
- Where two notes disagree on a candidate, both rows are kept and the next section says which one the kit follows.
- The note `second-look` (11 November, after the live runs) ranks the open rows and adds ten: what the pilot's own
  data says about the loop's keep rule, and what one further web reader found. `scout/draft/second-look.md` holds
  the measurements and the order in which to build what is open.
- Its first group, what makes the loop's decisions trustworthy, was built on 11 November at the user's word
  (`scout/covered/built-package-a.json`): the keep rule's noise pooled over all seed panels, a self-test of the
  evaluator before a campaign, an accepted way for a session to propose nothing, a confirmation on fresh seeds
  when a campaign ends, and a final evaluation that is single-use and leaves a receipt. Eight rows became
  finished; six are still unfinished because only a part of what they describe is built, and each says which
  part. Comparing runs seed by seed, which the first row also named, was measured in round 2 and rejected. Of
  the other groups of that note, round 2 built three items (next section); the rest is not built.
- On 12 November four rows were added to the same note for candidates the user asked about and no note held:
  fine-tuning on a stronger agent's solved traces before RL (Trial), harness adapters (Hold), safeagents with
  atif-scan (Assess) and the Plurai Simulation plugin (Hold). None was tried (`scout/draft/second-look.md`,
  "Asked afterwards").

## Round 2 (12 November 2026)

The user's second prompt (`docs/upgrade/ROUND2.md`) asked for a comparison of the kit with similar projects as
wholes, for newer methods in place of the kit's defaults, and for a decision on everything still open. It ran
under the same usage limit as the first round.

- Census. `scout/census.md` lists the systems read at their source, each with version or commit and date, a
  capability matrix with the kit as one column, the candidates and four whole-system alternatives. Its rows are
  the notes `census-loops` (15 rows) and `census-harnesses` (17). No system read does the kit's whole job better.
  What two or more strong systems share and the kit lacks is a row now: a repair attempt after a crash, a restart
  on a stall, combining two candidates, memory across campaigns, evaluation in parallel, a review of the diff
  before training.
- Newer methods. The note `newer-methods` (9 rows) holds what a search by date found for the kit's defaults. The
  note `round2` (41 rows) holds the kit's own open items and the claims of a third report the user supplied on
  12 November: another model's audit of the kit, with patches and four modules. Each claim was checked against the
  kit's code or the claim's source before it got a row (`scout/draft/third-report-claims.md`). Nine of its
  rows are what the independent review of the round led to (last point of this section), and its last two rows
  are faults in remote runs that the full test runs exposed: the time a paid run is booked for, and a stale file
  in the mirror of a rented job.
- Measured here. The run-to-run noise of the benchmark: 32 runs, two commits on eight seeds, each run twice. Most
  of the noise lies between seeds, and the seed means of the two commits correlate at r = 0.30 only. Also measured:
  e-means against FAISS k-means on 200,000 synthetic vectors (`references/data.md`, section 8).
- Simulated, not measured. Rules for the loop's decisions were compared on simulated campaigns: the kit's own rule
  code on synthetic scores, in units of the run-to-run standard deviation, with three seeds, 34 runs and 10,000 or
  20,000 campaigns per variant. Of the ideas, 45 % are harmful, 35 % have no effect and 20 % are a gain, which is
  how the campaign of 12 November looked; two poorer mixes ran beside it. A row that says "simulated" rests on
  this model. It ranks rules against each other. It does not show a gain on the benchmark.
- Built (`scout/covered/built-round2.json`). In the loop: a near-miss is decided on a second seed panel; the worker
  sees a few points of the best run's curves and both scores of a first-seed discard; a campaign stops when a
  session that used tools left no guard record. In the guard: every registered worktree of the repository is
  covered, `git show <rev>:<sealed path>` is denied, and unattended read tools reach linked paths through the
  loop's worktree. In the references: e-means as the optional method for clustering embeddings.
- Rejected on these measurements: comparing seed by seed (at three seeds the correlation does not pay for the
  degrees of freedom it costs), an anytime-valid rule for the loop (fewer gains kept per campaign at the same
  number of runs), every variant of the first-seed gate, a first baseline of twice the seeds, and re-measuring a
  kept commit before it becomes the baseline.
- From the third report. Two of its defect claims were right and are fixed (the `git show` route to a sealed
  file, linked paths under unattended read tools). Rejected, each with the reason in its row: its four modules,
  edit markers in the training script, the claims that the code does not bear out (links in snapshots, the thinned
  curve, the remote ledger) and those that describe a deliberate design (a worktree is a project of its own, one
  copy of the sealed rules). Two of its ideas are undecided: a read-only `expctl compare`, and showing later
  workers the diffs of inconclusive changes.
- Open after round 2. The undecided rows with the highest expected benefit are numeric settings searched by the
  harness, a fine-tuning track with a second benchmark task, a restart on a stall and a repair attempt after a
  crash. The Adopt rows that were unfinished before round 2 still are, among them a minimum agent version, the
  doctor report, a job object per run on Windows and a checkpoint helper. The reason is the same usage limit.
- Tools as of 12 November. One release changes a decision: FAISS 1.16.0 (10 November) carries e-means. The
  optuna-mcp repository has new commits (22 October), which changes the reason for not adopting it, not the
  decision.
- Live check. One campaign with a real agent ran on the changed loop (headless Claude Code 2.1.322, native
  Windows). The second seed panel turned one near-miss into a keep on six seeds, and the confirmation on fresh
  seeds found that gain inside the noise: verdict unclear (report, "Round 2").
- Independent review. One reviewer without the working context reviewed the round's changes to the guard, the
  loop's decisions and the final evaluation: 19 findings. The round's commits introduced no blocking flaw; the
  worst finding is older than the round (sealed data behind a link to storage outside the repository was
  readable). Fixed with tests in commits `af6cbeb` (guard) and `7c1306f` (loop, final evaluation, self-test):
  five Adopt rows. Answered and not built, each a Reject row with its reason: a guard rule for git commands
  that print tracked files without naming them, a refusal of every call when the session's `.git` pointer is
  damaged, keeping a partly trained second panel across a stop, and detecting a forged guard record. A probe
  of my own after the fixes found that a search of a linked data folder still read sealed files in five of
  eleven layouts, where ripgrep 15.2.0 was the reference; closed in commit `98640c9` (same row as the link
  finding).
- The tables below cut every cell at 300 characters. The notes hold the full text.

## Rounds 3 and 4 (12 and 13 November 2026)

Both rounds built from the order that round 2 left, under the same usage limit. Neither did research beyond what
a build needed.

- Round 3 (`scout/covered/built-round3.json`), in a session of its own: numeric settings searched by the harness
  (opt-in, `loop.search_trials`), a second benchmark task that fine-tunes a small language model, and a restart
  when a campaign stalls (opt-in, `loop.restart_after`). Three rows became finished.
- Round 4, the first four items of a ranked list the user asked for (note `round4`, 7 rows;
  `scout/covered/built-round4.json`). In the guard: a question before a recursive command over the project root
  when sealed files lie on disk below it, which closes the gap the 23 October guard kept; a search that walks each
  folder once; folder changes in more forms; files of another checkout judged by the rules of that checkout. In
  the installer: `--worktrees`, which registers the guard for sessions started in the repository's other
  checkouts, and a warning in `expctl selftest` about checkouts without it. For the subagents: `onFailure: block`
  on their own hook. In the loop's self-test: no score for a folder that holds only a run's records, the run's
  score for a copy whose records and log state other values, and controls (`loop.controls`) that cannot have
  learned the task and must stay at their floor; the character-model task has two. Four rows that were unfinished
  became finished.
- Measured in round 4. The harness's search of numeric settings, on and off, on both benchmark tasks with the
  stand-in agent, three pairs of campaigns per task at 18 runs. Fine-tuning task: confirmed gain 0.42 with the
  search against 0.31 by hand. Character model: nothing kept in either arm. By the rule fixed before the
  measurement (a gain on both tasks) the search stays off by default. Not measured with a real agent.
- Round 3's repairs, looked at again in round 4 at the user's word: five faults beside them were fixed in
  `expctl.py`, `runlog.py` and `nnremote.py` (report, "Round 4").
- Independent review of round 4. Two reviewers without the working context: 11 findings on the guard and 7 more
  in a second look at the fixes, 10 on the installer and the loop. All are fixed or answered. Two of the guard
  findings were holes that round 4's own root check had opened; they were closed before the round reached the
  main branch. Answered and not built, each a Reject row with its reason: reading program text for moves and
  reads of sealed folders, and moving more than the numbers with a fraction in the self-test's copy. The fixes
  to the second look's findings and to the installer and loop findings were verified by probes and tests, not
  reviewed again.
- Open after round 4. Undecided, with the highest expected benefit: a repair attempt after a crash, controls for
  the fine-tuning task, a campaign with a real agent that uses the search. The Adopt rows that round 2 named as
  unfinished still are: a minimum agent version, the doctor report, a job object per run on Windows, a checkpoint
  helper.

## Recommended combination

`references/stack.md` names it and gives each pin with its source: uv 0.13.7; PyTorch 2.15.0 (`cu132` wheels); the
kit's run directory as the record, with Trackio 0.45.0 as an optional mirror; Optuna 5.0.0; lm-evaluation-harness
0.4.13 in its own environment (sacreBLEU 2.6.0); `nnremote` over ssh or Hugging Face Jobs (huggingface_hub 2.4.0);
Context7 MCP 4.6.0 and the Hugging Face MCP server v0.4.34 through `install.py --mcp`; for fine-tuning Transformers
5.22.2, TRL 1.17.1, PEFT 0.21.2 and bitsandbytes 0.50.2. Round 2 adds one optional pin for one job: `faiss-cpu`
1.16.0, only where a data step has to cluster embeddings.

Tried on 2026-11-11 in throwaway environments in WSL2 (Ubuntu 24.04, Python 3.12, RTX 5090, driver 596.49): every
pin above resolves and installs. Working: uv 0.13.7 (`uv add`, `uv sync --locked`, `uv run --frozen`, the one-week
cooldown), Optuna 5.0.0 (a 15-trial study), sacreBLEU 2.6.0 (a score with its signature), Trackio 0.45.0 (a local
log), lm-evaluation-harness 0.4.13 (installs in its own environment and its command starts; no task was run),
Transformers, TRL, PEFT and bitsandbytes at their pins (install together and import), and the `hf` command of
huggingface_hub 2.4.0 (its help lists every flag and bucket command that `nnremote` calls). **Not working: PyTorch
2.15.0+cu132 on the GPU.** It installs and runs on the CPU, but its first CUDA call crashes the interpreter in WSL2
(segmentation fault inside the `cuda-bindings` package; cause not found), while torch 2.9.1+cu128 trains on the
same GPU. The kit's benchmark therefore did not run on the pinned build. The two MCP servers were not connected:
the installer's merge is tested, nothing more. Nothing in this list was used for real training.

Tried on 2026-11-12 on native Windows (Python 3.11, a throwaway environment, CPU): `pip install faiss-cpu==1.16.0`
installs, and `faiss.contrib.e_means.NumpyEmeans` clusters 200,000 vectors as `data.md` section 8 reports. The GPU
build and a real corpus were not tried.

Two things the kit uses come from Trial rows, because they could be tested here: the bubblewrap run wrapper of the loop
(tested in WSL2) and the Hugging Face Jobs route (tested against a stand-in command only).
