# Scout note: unattended operation, sandboxing, security and supply chain

Written 2026-11-11 (research done 2026-11-10 and 2026-11-11). Draft input for the design step, not a decision.

Conventions

- Status: **Verified** = read in a primary source on the date given. **Inferred** = reasoned from verified facts, from absence in a primary source, or from a secondary reading of source code. **Unverified** = user-generated or secondary sources only, memory, or not reachable.

## Summary (10 lines)

1. No agent sandbox examined can host a GPU training run launched the way the kit launches it: bubblewrap-based sandboxes hide the GPU device nodes and end child processes when the command returns, and the Windows process container does the same and has no GPU policy.
2. So an unattended design needs one of two shapes: the run launcher sits outside the agent's sandbox (excluded command or a host-side broker), or agent and run live together in a GPU-capable container. Only the second allows approvals to be bypassed.
3. Without a container, the Claude Code recipe is `--permission-mode dontAsk` plus explicit allow rules plus `--permission-prompts none`, with budget and turn caps and the retry watchdog. Denied calls do not stop a headless run, so the harness must read the denial list and the exit status itself.
4. The guard hook can be absent without any error (`--bare`, announced as the future default for `-p`; an untrusted workspace; Windows fail-open bugs fixed only in 2.1.309 to 2.1.316). An unattended session must prove the guard is live before it starts and require a minimum agent version.
5. Native Windows has no sandbox for Claude Code. What exists without administrator rights (job objects, restricted tokens, the new process container) gives process-tree control or partial isolation, not a GPU-capable no-network sandbox. On native Windows the honest label is "allow-list and hooks only".
6. Prompt injection is unsolved (surveys: over 85% adaptive attack success, most defences under 50%). Since 23 October: skill poisoning that evades scanners, an allow-listed model hub used as a covert channel, a plugin commit-pin bypass, and editor-agent sandbox escapes through a writable virtual environment, git hooks and hook configuration.
7. The practical answer is structural: scouting sessions get the web but no shell, no secrets and no instruction-file writes; experiment sessions get the shell but no web; fetched text is stored as data with provenance; the evaluator and the guard must not depend on anything the agent can write.
8. Two 2026 PyPI compromises of ML packages harvested environment variables and credential files; one was live for about 40 minutes. Installs from a lock file made earlier would have skipped both, and a release-age cooldown (now built into uv, pip and npm) covers the fresh-release window. Install-time verification of PyPI attestations was not found.
9. The kit's own controller is the largest secret leak: it hands every run the whole environment, writes it to a file on one path, and links git-ignored files into snapshots. A standard-library environment allow-list, redaction and snapshot exclusions fix this; agent-side scrubs are partial and, on Linux, break run control.
10. For hours-long work, drive fresh headless sessions from a small loop or an OS scheduler with a state file. Agent-native schedulers are session-bound (7-day expiry), app-bound or cloud-only. WSL2 stops an idle distribution after 15 seconds by default; `instanceIdleTimeout=-1` is now documented.

## Q1. Isolating an unattended agent and its training runs

### Linux and WSL2

- Q1.1 Claude Code's built-in sandbox runs on macOS (Seatbelt), Linux and WSL2 (bubblewrap plus a socat-based proxy). On native Windows commands run unsandboxed. It covers shell commands only: file tools, MCP servers and hooks run outside it. `[https://code.claude.com/docs/en/sandboxing | docs at v2.1.322 | 2026-11-10 | Verified]`
- Q1.2 Defaults: writes confined to the working directory; reads allowed across most of the machine (home SSH keys included) unless denied; the allowed-domain list starts empty; the sandboxed command inherits the agent's environment including secrets; there is no built-in credential deny list. Tightening settings: `sandbox.failIfUnavailable`, `sandbox.allowUnsandboxedCommands: false`, `sandbox.credentials` (files and envVars, `deny` or `mask`), `strictAllowlist` (v2.1.219+). Commands in `excludedCommands` run outside the sandbox. `[https://code.claude.com/docs/en/sandboxing | v2.1.322 | 2026-11-10 | Verified]`
- Q1.3 Documented limits: not a complete isolation boundary; the proxy does not inspect TLS; broad allowed domains such as a code host are exfiltration paths; allowing the container-runtime socket hands over the host; `docker` does not work inside the sandbox; `enableWeakerNestedSandbox` weakens it; subagents use the parent's sandbox settings. `[https://code.claude.com/docs/en/sandboxing | v2.1.322 | 2026-11-10 | Verified]`
- Q1.4 Vendor position on unattended use: the sandboxed Bash tool alone is not enough for fully unattended runs; bypass mode belongs only inside a container, a VM or the sandbox runtime; the auto-mode classifier is a per-action control, not an isolation boundary; any setup that allows egress can still leak what the agent can read. `[https://code.claude.com/docs/en/sandbox-environments | v2.1.322 | 2026-11-10 | Verified]`
- Q1.5 Setup cost on Ubuntu: `sudo apt-get install bubblewrap socat`. Ubuntu 24.04 and later restrict unprivileged user namespaces through AppArmor, so bubblewrap may need a profile; v2.1.310 made `/sandbox` explain this. `[https://code.claude.com/docs/en/sandboxing and https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md | v2.1.310 entry, paraphrase | 2026-11-11 | Verified]` A user report says Ubuntu 26.04's stock profile denies a capability bubblewrap needs. `[https://github.com/anthropics/claude-code/issues/105194 | open issue | 2026-11-11 | Unverified]` Whether the WSL2 kernel applies this restriction at all was not tested. `[none | n/a | 2026-11-11 | Unverified]`
- Q1.6 GPU inside bubblewrap sandboxes. The docs say nothing. `--dev /dev` mounts a fresh minimal `/dev` without GPU nodes; they come back only with `--dev-bind` placed after it: `/dev/nvidia0`, `/dev/nvidiactl`, `/dev/nvidia-uvm` on native Linux, or `/dev/dxg` plus read-only `/usr/lib/wsl` plus writable own `/proc` entries on WSL2 (CUDA writes a thread name there during start-up). Neither Claude Code nor the sandbox runtime has a setting for device binds; the request has been open since 2025-12-05. The workaround people use is to run that one command unsandboxed. `[https://github.com/anthropics/claude-code/issues/13108 (open, updated 2026-08-17, comment on v2.1.89 dated 2026-04-13); https://github.com/anthropics/claude-code/issues/64530; https://github.com/openai/codex/issues/22469; https://github.com/openai/codex/issues/19676; https://github.com/NVIDIA/OpenShell/pull/608 | issue trackers | 2026-11-11 | Inferred: user reports that agree across three independent repositories, no vendor document]`
- Q1.7 The sandbox runtime always passes `--new-session --die-with-parent --unshare-pid --dev /dev` to bubblewrap and adds `--unshare-net` when the network is restricted. Background or detached children (setsid, nohup, double fork) are killed when the sandboxed command exits. There is no setting to bind host devices or keep the host PID namespace. `[DeepWiki reading of https://github.com/anthropics/sandbox-runtime source | v0.0.82 | 2026-11-11 | Inferred (secondary reading of source)]`
- Q1.8 Sandbox runtime (`srt`): Apache-2.0, labelled a beta research preview, v0.0.82 released 2026-11-09, repository created 2025-10-20, about 7,070 stars. It wraps any process, including the whole agent (`srt claude`) or a single MCP server; settings in `~/.srt-settings.json`; needs bubblewrap 0.4.0 or later, socat and ripgrep on Linux. The repository now lives under the `anthropics` organisation. `[https://github.com/anthropics/sandbox-runtime and https://github.com/anthropics/sandbox-runtime/releases/tag/v0.0.82 | v0.0.82 | 2026-11-11 | Verified]`
- Q1.9 bubblewrap itself: latest 0.13.1 (2026-10-14). `[https://github.com/containers/bubblewrap/releases/tag/v0.13.1 | 0.13.1 | 2026-11-11 | Verified]` `--unshare-net` leaves the process with a new network namespace that has only loopback. `[bubblewrap man page, not re-read | n/a | 2026-11-11 | Inferred]`
- Q1.10 Docker with no network: the `none` driver creates only the loopback device in the container. `[https://docs.docker.com/engine/network/drivers/none/ | page as served | 2026-11-11 | Verified]`
- Q1.11 Docker GPU on WSL2: supported with the latest NVIDIA Container Toolkit through the Docker CLI or Docker Desktop; only `--gpus all` is supported; pinned system memory is limited so some training workloads may fail; NVML queries are partial. `[https://docs.nvidia.com/cuda/wsl-user-guide/index.html | updated 2026-11-02 | 2026-11-11 | Verified]` Toolkit 1.20.1 (2026-09-19) fixes `NVIDIA_VISIBLE_DEVICES=none` on WSL2. `[https://github.com/NVIDIA/nvidia-container-toolkit/releases/tag/v1.20.1 | 1.20.1 | 2026-11-11 | Verified]` Docker Desktop passes GPUs only with the WSL2 backend. `[https://docs.docker.com/desktop/features/gpu/ | page as served | 2026-11-11 | Verified]`
- Q1.12 `docker run --network none --gpus all` together is documented nowhere I could find. `[the three pages above | n/a | 2026-11-11 | Inferred: expected to work, needs a local trial]`
- Q1.13 Dev containers: the spec has `hostRequirements.gpu` (true, `"optional"` or an object), `runArgs` (raw Docker arguments, the usual place for `--gpus all`), `capAdd`, `mounts`, `containerEnv` and `remoteEnv`; `initializeCommand` runs on the host. `[https://containers.dev/implementors/json_reference/ | spec page as served | 2026-11-11 | Verified]`
- Q1.14 Claude Code's reference dev container: feature `ghcr.io/anthropics/devcontainer-features/claude-code:1.0`; its firewall script needs `NET_ADMIN` and `NET_RAW`; with bypass mode the container does not stop a malicious project from exfiltrating anything reachable inside, including the agent credentials in `~/.claude`; pin the CLI (`npm install -g @anthropic-ai/claude-code@X.Y.Z`) and set `DISABLE_AUTOUPDATER=1`; a long-lived token from `claude setup-token` goes in `CLAUDE_CODE_OAUTH_TOKEN`. `[https://code.claude.com/docs/en/devcontainer | v2.1.322 | 2026-11-10 | Verified]`
- Q1.15 Docker Sandboxes (`sbx`): a microVM with its own kernel and private Docker engine; outbound TCP goes through a host proxy that enforces policy; UDP is off by default; credentials are injected by the host proxy and not stored in the VM; SSH agent forwarding is on by default; local stdio MCP servers run on the host, outside the VM. `[https://docs.docker.com/ai/sandboxes/security/isolation/ | page as served | 2026-11-11 | Verified]`
- Q1.16 Docker Sandboxes setup: local use is free but needs a Docker account sign-in (`sbx login`); Windows 11 needs the Windows Hypervisor Platform feature (enabling it needs an elevated prompt; the per-user install does not); Ubuntu 24.04+ needs KVM and membership of the `kvm` group. `[https://docs.docker.com/ai/sandboxes/install/ | page as served | 2026-11-11 | Verified]`
- Q1.17 Docker Sandboxes GPU passthrough is experimental, works only on x86_64 Linux hosts, binds an NVIDIA GPU that nothing else uses to VFIO (the host loses it), and needs a driver bundle rebuilt for each release; flags `sbx settings set feature.sandbox-gpu true` and `--gpu`. Not usable for GPU runs on a one-GPU Windows machine. `[https://docs.docker.com/ai/sandboxes/configuration/gpu-passthrough/ | page as served | 2026-11-11 | Verified]`
- Q1.18 WSL containers (`wslc.exe`): settings in `%LOCALAPPDATA%/wslc/settings.yaml` (`session.cpuCount`, `memorySize`, `idleTimeout` default 30 s); `.wslconfig` does not apply; no GPU key is listed. `[https://learn.microsoft.com/en-us/windows/wsl/wsl-container-settings | ms.date 2026-10-16 | 2026-11-11 | Verified]`

### Native Windows (what exists without administrator rights)

- Q1.20 Sandbox runtime on Windows: an alpha backend (a dedicated local user plus a Windows Filtering Platform fence; one elevation prompt at install; a sandboxed command cannot outlive its session), and from v0.0.82 an opt-in process-container backend (`windows.backend: 'mxc'`, Node 24+, optional `@microsoft/mxc-sdk`; MSYS2 programs, Git Bash included, do not run under it yet). `[https://github.com/anthropics/sandbox-runtime README and release v0.0.82 | v0.0.82 | 2026-11-11 | Verified]`
- Q1.21 Microsoft MXC process isolation: no administrator rights; needs Windows 11 24H2 build 26100.9278 or 25H2 build 26200.9278 (session isolation needs .9550); MIT licence; SDK v1.0.1 (2026-10-17); outbound network denied through the filtering platform without an elevation prompt per launch; child processes end when the launcher exits. `[https://github.com/microsoft/mxc and https://github.com/microsoft/mxc/blob/main/docs/backends/process-container/os-version-support.md | SDK v1.0.1 | 2026-11-11 | Verified]` Its process-container policy has no GPU field (only the WSL-container backend has a `gpu` switch). `[same | SDK v1.0.1 | 2026-11-11 | Inferred from absence]`
- Q1.22 Codex on Windows offers `mxc` (recommended, no admin), `elevated` and `unelevated` sandbox modes; remaining child processes stop when the foreground command exits; a probe command exists from CLI 0.162.0. `[https://learn.chatgpt.com/docs/windows/windows-sandbox | CLI 0.167.0 current | 2026-11-10 | Verified]`
- Q1.23 Job objects group processes and can enforce working-set, priority, time and process-count limits, terminate the whole group, and kill everything when the last handle closes (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`). Children join the job by default; nesting works since Windows 8. Security limits are per process: a job gives no file or network isolation. `[https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects | ms.date 2025-07-14 | 2026-11-11 | Verified]` No administrator right is mentioned. `[same | same | 2026-11-11 | Inferred]`
- Q1.24 Restricted tokens can drop privileges, mark group identifiers deny-only and add restricting identifiers; an ordinary application may start a process with a restricted copy of its own token; the page recommends a separate desktop and says nothing about the network. `[https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens | ms.date 2018-05-31, updated 2025-03-12 | 2026-11-11 | Verified]`
- Q1.25 AppContainer gives credential, device, file, network, process and window isolation; the page does not state whether administrator rights are needed. `[https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation | ms.date 2025-07-08 | 2026-11-11 | Verified]`
- Q1.26 Windows Sandbox: Pro, Enterprise and Education only; an optional Windows feature (the PowerShell route needs an Administrator prompt, a restart may follow); disposable; one instance at a time; networking on by default (`<Networking>Disable</Networking>` in a `.wsb` file turns it off); `<MappedFolders>` with `<ReadOnly>`; the virtual GPU is on by default and documented as widening the attack surface; CUDA is not mentioned. Not a place to train. `[https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-install and .../windows-sandbox-configure-using-wsb-file | ms.date 2026-03-29 | 2026-11-11 | Verified]`
- Q1.27 Per-program firewall rules need elevation. `[general knowledge, page not fetched | n/a | 2026-11-11 | Unverified]`

### Other agents' sandboxes

- Q1.28 Codex: network off by default; Linux uses bubblewrap plus seccomp; `codex exec` runs in a read-only sandbox unless `--sandbox workspace-write` is passed; `--full-auto` is no longer supported; `--ask-for-approval never` disables prompts; inside writable roots `.git`, `.codex`, `.agents` and `.aws` stay read-only; in Docker the docs say to run with `danger-full-access` inside the container. `[https://learn.chatgpt.com/docs/agent-approvals-security and https://learn.chatgpt.com/docs/non-interactive-mode | CLI 0.167.0 (2026-11-06) | 2026-11-11 | Verified]` GPU inside the Codex Linux sandbox has the same device problem; users widen `writable_roots` to `/dev` as a workaround. `[https://github.com/openai/codex/issues/3141 | issue | 2026-11-11 | Unverified]`
- Q1.29 Cursor: Seatbelt on macOS (Cursor 2.0+); Landlock plus seccomp on Linux (kernel 6.2+ with Landlock v3 and unprivileged user namespaces; where those are missing Cursor asks for approval before each command instead). Run modes are Auto-review (default, shipped in 3.6), Allowlist and Run Everything. Network is blocked by default and then opened by the network mode: the default mode (`sandbox.json + Defaults`) adds a built-in allow-list for package managers and language tools that includes a code host and package registries, `sandbox.json Only` uses only the project's list, `Allow All` opens everything. So the default mode leaves an exfiltration path and an install path open (see Q2.21). The page does not mention Windows. `[https://cursor.com/docs/agent/security/run-modes | page as served | 2026-11-11 | Verified]` The vendor's engineering post adds a bubblewrap fallback on Linux and WSL2 as the Windows route. `[https://cursor.com/blog/agent-sandboxing | 2026-02-18 | 2026-11-10 | Verified]` `sandbox.json` keys: `type` (`workspace_readwrite`, `workspace_readonly`, `insecure_none`), `networkPolicy.default` (`deny` by default), `networkPolicy.allow`, `readBoundary` (needs Cursor 3.23+), `additionalReadwritePaths`. Always write-protected: `.cursor` and `.claude` JSON files, `.vscode/`, `.git/hooks/`, `.git/config`, `.cursorignore`. The `.cursor` sub-folders `rules/`, `skills/`, `agents/` and `commands/` stay writable by the sandboxed agent. `[https://cursor.com/docs/reference/sandbox | page as served | 2026-11-11 | Verified]` The run-modes page has an AppArmor section for the standalone CLI, which implies the terminal agent is sandboxed on Linux; it is not said outright, and how a headless run selects the network mode and what happens to child processes are not stated. `[https://cursor.com/docs/agent/security/run-modes | page as served | 2026-11-11 | Unverified]` If the test machine's Cursor is 3.2 as the upgrade prompt records, it predates Auto-review (3.6) and `readBoundary` (3.23). `[docs/upgrade/PROMPT.md and the pages above | as given | 2026-11-11 | Inferred]`

### What this means for the kit

- Q1.30 A detached training run cannot be started from inside any of these sandboxes, and the GPU is not visible there. The launcher must run outside the sandbox boundary, or the agent and the run must share one GPU-capable container. `[Q1.6, Q1.7, Q1.21, Q1.22 | n/a | 2026-11-11 | Inferred; needs a local trial on WSL2]`
- Q1.31 The only route with documented GPU passthrough on the test machine is a Linux container under WSL2 (`--gpus all`). A training run needs no network, so `--network none` fits a run container; the agent's container needs egress to its API, so it needs an allow-list firewall instead. `[Q1.10 to Q1.14 | n/a | 2026-11-11 | Inferred]`
- Q1.32 Giving the agent the container-runtime socket so it can start run containers equals giving it the host. A user-started host-side broker that picks up run requests from a directory avoids that. `[Q1.3 | n/a | 2026-11-11 | Inferred]`
- Q1.33 On native Windows a named job object is the standard-library way (through `ctypes`) to stop a whole run tree and cap its memory. It is not a security boundary. If the agent itself runs its commands in a job with kill-on-close, a detached run may die with it; this was not tested. `[Q1.23 | n/a | 2026-11-11 | Inferred]`

## Q2. Prompt injection and tool abuse

### Documented attacks, 2025 to 2026

- Q2.1 A systematisation of 78 studies (2021 to 2026) on agentic coding assistants lists 42 attack techniques and 18 defences; adaptive attacks pass state-of-the-art defences more than 85% of the time and most defences stop less than half of adaptive attacks. Measured by the authors from published studies. `[https://arxiv.org/abs/2601.17548 | 24 Jan 2026 | 2026-11-11 | Verified (abstract)]`
- Q2.2 Tool-poisoning tests on seven MCP clients found very uneven guardrails. `[https://arxiv.org/abs/2603.21642 | 23 Mar 2026 | 2026-11-11 | Verified (abstract)]`
- Q2.3 Skill poisoning: procedural payloads planted in third-party skills (566 target skills, 5,244 requests, over 26,000 registry entries) mostly evade a dedicated skill scanner and an LLM judge and succeed end to end in a Claude Code workflow with a current frontier model. `[https://arxiv.org/abs/2611.12155 | 9 Nov 2026, preprint | 2026-11-11 | Verified (abstract)]`
- Q2.4 Approval laundering: one approval covers one invocation, but its effects are transitive (package install lifecycle scripts, MCP network use); a policy that only records approvals cannot guarantee coverage; a PreToolUse integration cut residual cases from 40 to 13 of 111. `[https://arxiv.org/abs/2609.28586 | 23 Sep 2026 | 2026-11-11 | Verified (abstract)]`
- Q2.5 Hidden text in papers: 18 arXiv manuscripts in July 2025 carried instructions for AI reviewers in white or microscopic text. A scouting agent that reads PDFs sees text a person does not. `[https://arxiv.org/abs/2507.06185 | v1 2025-07-08, v2 2026-08-17 | 2026-11-11 | Verified (abstract)]`
- Q2.6 Covert exfiltration through an allow-listed host: CVE-2026-54316 (GHSA-fg94-h982-f3mm), Claude Code 0.2.54 up to before 2.1.163. The bare host of a model hub was pre-approved for WebFetch, so attacker-controlled repository paths were fetched with no prompt and outside `--allowedTools` limits, and download counters formed a channel. Patched in 2.1.163, published 2026-06-13, CVSS 6.0. `[https://github.com/anthropics/claude-code/security/advisories | page 1 of 4 | 2026-11-11 | Verified]`
- Q2.7 Pin bypass: CVE-2026-86063 (GHSA-pq7j-f95f-qfcv), Claude Code before 2.1.179. A plugin's commit pin was not verified after checkout; a branch named like the commit won. Published 2026-10-09, CVSS 7.7. `[https://github.com/anthropics/claude-code/security/advisories | page 1 of 4 | 2026-11-11 | Verified]`
- Q2.8 Other 2026 Claude Code advisories (titles and dates read): a race in the Edit tool that writes outside the workspace (GHSA-5xjx-9qx6-jcrv, 2026-10-26), an untrusted search path that runs a planted git executable (GHSA-4p2j-qj3c-6x84, 2026-10-13), symlink following on write (GHSA-5j29-h97v-84ch, 2026-10-05), sandbox escape through git worktree path confusion (GHSA-7835-87q9-rgvv, 2026-06-25). `[https://github.com/anthropics/claude-code/security/advisories | page 1 of 4 | 2026-11-11 | Verified]`
- Q2.9 Cursor advisories: sandbox escape by replacing the virtual environment's Python executable, which an editor extension later runs unsandboxed (CVE-2026-73217, before 3.1.2, 2026-07-14); escapes through privileged containers (2026-07-14), through another agent's hook configuration (2026-05-21) and through git hooks (2026-02-13); two critical path-handling issues (2026-06-05). `[https://github.com/cursor/cursor/security/advisories | page 1 of 4 | 2026-11-11 | Verified]`
- Q2.10 Claude Code releases 2.1.309 to 2.1.321 fixed a series of permission-check gaps: a crafted environment prefix hiding part of a command, deny rules missing commands with quoted words, `sed` skipping the check, a read-only command running outside the sandbox, `cp` or `mv` evading deny rules, a worktree sandbox escape, sandboxed commands able to edit the file passed with `--mcp-config`. Pattern rules in permission lists and hooks are best effort. `[https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md | 2.1.309 to 2.1.321, paraphrase | 2026-11-11 | Verified]`

### What vendors recommend

- Q2.11 Anthropic: `curl` and `wget` are not auto-approved; for most fetches WebFetch returns a separate model call's answer about the page instead of the raw page; a `-p` session shows neither the workspace-trust dialog nor the `.mcp.json` approval; do not pipe untrusted content into the agent; use VMs for scripts and tool calls that touch external services; the vendor does not audit MCP servers; `ConfigChange` hooks can audit or block settings changes. `[https://code.claude.com/docs/en/security | v2.1.322 | 2026-11-11 | Verified]`
- Q2.12 Anthropic's own measurement (browser use, adaptive attacker, 100 attempts per environment): 1.4% success against its best model with improved safeguards, 8.0% without; the company says the problem is not solved. Measured by the vendor. `[https://www.anthropic.com/research/prompt-injection-defenses | 2025-11-24 | 2026-11-11 | Verified]`
- Q2.13 OpenAI Codex: web search uses a cached index by default (`web_search = "cached"`; `"live"`, `"disabled"`) to reduce exposure to live injected content, and switches to live under full access; web results are to be treated as untrusted. `[https://learn.chatgpt.com/docs/agent-approvals-security | CLI 0.167.0 | 2026-11-11 | Verified]` Codex hooks are described as a guardrail and not a complete enforcement boundary; hosted tools such as web search are not covered by PreToolUse. `[https://learn.chatgpt.com/docs/hooks | CLI 0.167.0 | 2026-11-11 | Verified]`
- Q2.14 Meta's Agents Rule of Two: one session should hold at most two of (a) processing untrusted input, (b) access to sensitive systems or private data, (c) changing state or communicating externally; all three need human supervision or a fresh context. `[https://ai.meta.com/blog/practical-ai-agent-security/ | 2025-10-31 | 2026-11-11 | Verified]`
- Q2.15 OWASP LLM01:2025 lists seven mitigations (constrain behaviour, validate output formats, filter input and output, least privilege, human approval for high-risk actions, segregate and mark external content, adversarial testing) and says no foolproof prevention is known. `[https://genai.owasp.org/llmrisk/llm01-prompt-injection/ | LLM01:2025 | 2026-11-11 | Verified]` The OWASP Top 10 for Agentic Applications for 2026 was published 2025-12-09; its item names did not render and are not cited. `[https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/ | 2025-12-09 | 2026-11-11 | Verified date only]`

## Concerns any design must handle

- SEC-PROMPT-INJECTION: fetched pages, papers, repositories and tool results can carry instructions; no filter is reliable
- SEC-HIDDEN-TEXT-IN-DOCUMENTS: invisible text in papers reaches the agent but not the human
- SEC-SKILL-POISONING: third-party skills, plugins and instruction files that pass scanners
- SEC-MEMORY-POISONING: web-derived text persisted into memory or instruction files
- SEC-EXFIL-ALLOWED-DOMAIN: data leaves through a host on the allow-list
- SEC-APPROVAL-TRANSITIVE-EFFECTS: one approved command triggers install scripts, subprocesses and network use
- SEC-RULE-PATTERN-BYPASS: command-pattern rules in hooks and permission lists are best effort
- SEC-SANDBOX-SCOPE-SHELL-ONLY: file tools, tool servers and hooks run outside the sandbox
- SEC-SANDBOX-FAIL-OPEN: sandbox missing or half-initialised while commands still run
- SEC-SANDBOX-KILLS-DETACHED-RUN: children end when the sandboxed command returns
- SEC-SANDBOX-NO-GPU: device nodes hidden inside the sandbox
- SEC-PID-NAMESPACE-BREAKS-RUN-CONTROL: status and stop cannot see host processes
- SEC-PLATFORM-WITHOUT-SANDBOX: a first-class platform (native Windows) offers hooks and allow-lists only
- SEC-TCB-WRITABLE-INTERPRETER: evaluator or guard depends on an interpreter, packages or start-up files the agent can write
- SEC-CONFIG-SURFACE-WRITABLE: agent can edit settings, hooks, tool-server configuration, git hooks or its own instruction files
- SEC-HOOK-NOT-LOADED: guard silently absent (minimal mode, untrusted workspace, missing shell, hook error)
- SEC-HOOK-COVERAGE-GAP: tool paths the hook matcher does not see
- SEC-AGENT-VERSION-TOO-OLD: installed agent predates the fixes the design relies on
- SEC-BYPASS-OUTSIDE-CONTAINER: approvals bypassed without an isolation boundary
- SEC-CONTAINER-CREDENTIAL-EXPOSURE: agent credentials stored inside the container are readable by project code
- SEC-RUNTIME-SOCKET-HOST-ACCESS: handing the agent the container-runtime socket equals host access
- SEC-ENV-SECRET-INHERITANCE: runs and subprocesses receive the whole environment
- SEC-SECRET-IN-RUN-ARTIFACTS: logs, environment dumps, journal and transcripts hold credentials
- SEC-SECRET-IN-SNAPSHOT: ignored credential files copied or linked into snapshots
- SEC-SECRET-SCRUB-PARTIAL: name and value heuristics miss tokens
- SEC-SECRET-ON-RENTED-MACHINE: long-lived or broad credentials placed on a remote machine
- SUPPLY-UNPINNED-INSTALL: installs without versions and hashes
- SUPPLY-FRESH-RELEASE-COMPROMISE: a malicious release installed within hours of upload
- SUPPLY-INSTALL-TIME-CODE: source builds, post-install scripts and interpreter start-up files
- SUPPLY-AGENT-INITIATED-INSTALL: the agent adds or upgrades a dependency during the loop
- SUPPLY-PIN-BYPASS: pins that are not verified (mutable tags, branch named like a commit)
- SUPPLY-MODEL-FILE-CODE-EXEC: pickle-based checkpoints execute code on load
- SUPPLY-REMOTE-CODE-FLAG: loaders that run repository code on request
- SUPPLY-SCANNER-BYPASS: scanners for model files and skills are evadable
- SUPPLY-TOOL-AUTOUPDATE: the agent or a tool server changes version under a running loop
- OPS-USAGE-LIMIT-STALL: rate limit or usage cap stalls or ends the loop
- OPS-SILENT-DENIAL-CONTINUE: denied actions do not stop a headless run
- OPS-SAFETY-REFUSAL-UNDETECTED: a refusal looks like a normal turn end
- OPS-EXIT-CODE-AMBIGUITY: exit status alone does not say what happened
- OPS-BUDGET-CAP-KILLS-BACKGROUND: reaching the spend cap stops agent-owned background work
- OPS-AGENT-EXIT-KILLS-RUN: agent exit or signal ends child processes
- OPS-BACKGROUND-TIME-LIMIT: agent-owned background commands have a time limit
- OPS-COST-ESTIMATE-CLIENT-SIDE: the reported spend is an estimate
- OPS-VM-IDLE-SHUTDOWN: the Linux subsystem's idle shutdown stops a detached job
- OPS-TEMP-DIR-WIPED: temporary folders emptied at restart
- OPS-SCHEDULE-EXPIRY: agent-native schedules expire or need an app open
- OPS-SCHEDULE-NO-CATCHUP: missed fires are not run later
- OPS-STATE-RESUME: resume does not restore running work or loops
- OPS-COMPACTION-STATE-LOSS: compaction drops loop state or reloads stale instructions
- OPS-HOST-SLEEP-OR-REBOOT: sleep, updates or logoff end a long run (not researched)
